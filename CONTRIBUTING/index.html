Contributing¶

Contributions are welcome. This guide covers the development setup and contribution workflow.

Required tools¶

Two external tools must be installed separately (not managed by uv sync):

The uv package manager¶

# macOS/Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Or via package manager
brew install uv

uv documentation

The just command runner¶

# macOS/Linux
curl --proto '=https' --tlsv1.2 -sSf https://just.systems/install.sh | bash

# Or via package manager
brew install just

just documentation

Ways to contribute¶

Report bugs¶

Report bugs at https://github.com/TUW-GEO/canvodpy-extensions/issues. Include your operating system, your setup, and the steps to reproduce.

Fix bugs and implement features¶

Issues tagged "bug"/"enhancement" and "help wanted" are open for contributions.

Add a new package¶

New extension packages live under packages/<name>/ and are picked up automatically by the uv workspace (packages/*). Each package is versioned on its own and published to PyPI (see Releasing below). A package lists every dependency it needs, with no extras. See packages/canvod-filemap for the expected layout (pyproject.toml, src/, tests/, README.md).

Development workflow¶

  1. Install required tools (uv and just).

  2. Fork and clone the repository: 

    git clone git@github.com:your_name_here/canvodpy-extensions.git
cd canvodpy-extensions

  3. Install dependencies: 

    uv sync
just hooks

  4. Create a feature branch: 

    git checkout -b name-of-your-bugfix-or-feature

  5. Make changes and verify: 

    just test
just check

  6. Commit using conventional commits: 

    git commit -m "feat(filemap): add support for recipe overrides"

  7. Push and create a pull request: 

    git push origin name-of-your-bugfix-or-feature
    A maintainer reviews and merges it. Coding agents may push the feature branch and open the pull request, but never merge, push main or tags, or bypass a check (AGENTS.md, Git and GitHub).

Commit message format¶

<type>(<scope>): <subject>

Types: feat, fix, docs, refactor, test, chore, perf, ci

Scopes: filemap, airflow, adapters, deps, ci, docs, release

Examples: 

git commit -m "feat(filemap): add recipe-based mapping for non-canonical filenames"
git commit -m "fix(filemap): handle missing site config gracefully"
git commit -m "docs: update installation instructions"

See Conventional Commits for the full specification.

Common commands¶

just --list                    # Show all commands
just test                      # Run all tests
just test-coverage             # With coverage report
just check                     # Lint + format + type-check

Coding agents¶

AGENTS.md (root and per package) holds the instructions for coding agents; the CLAUDE.md files import it. Task guides for agents are in .claude/skills/. Keep them correct when you change what they describe; just check-agent-docs checks that the paths and recipes they name exist.

Pull request guidelines¶

  1. Include tests for new features. New code must not reduce test coverage.
  2. Update the package's README.md and the Zensical documentation in docs/ if adding or changing public API or behavior.
  3. Ensure compatibility with Python 3.14+.
  4. Add yourself to CONTRIBUTORS.md if this is your first contribution.

Licensing¶

canvodpy-extensions is licensed under the Apache License 2.0. By submitting a pull request, you agree that your contribution is licensed under the same terms. The LICENSE and NOTICE files at the repository root apply to all source files. Per-file license headers are not required.

Code quality¶

  • ruff for linting and formatting
  • ty for type checking
  • pytest for testing with coverage

Run just check before committing.

Releasing¶

Releases are cut by a maintainer, never by a coding agent; only maintainers can create release tags.

Each package is versioned and released on its own. A release is the git tag <package>-v<version>, for example canvod-filemap-v0.2.0, on main.

just versions                         # current version of every package
just changelog canvod-filemap         # changes since its last release
just release canvod-filemap minor     # or major, patch, or for example 0.2.0

just release runs the package's tests and makes one commit that

  • sets the version in packages/<package>/pyproject.toml (and uv.lock),
  • writes packages/<package>/CHANGELOG.md from the commits that changed packages/<package>/ (git-cliff, cliff.toml).

Commit messages become the changelog, so follow the commit convention here and mark breaking changes (feat!: or a BREAKING CHANGE: footer).

main requires a PR (branch protection), so the tag is set after the merge:

git checkout -b chore/release-canvod-filemap-0.2.0   # before just release
just release canvod-filemap 0.2.0
git push -u origin chore/release-canvod-filemap-0.2.0
gh pr create --fill
# once merged:
git checkout main && git pull
just tag canvod-filemap                # tags main and pushes the tag

(Don't tag before the PR merges: a merge can produce a different commit SHA than the one you tagged, orphaning the tag.)

Pushing the tag runs release.yml, which checks that the tag matches the package version and drafts a GitHub Release with the tag's section of the package's CHANGELOG.md. Publish the draft by hand. Publishing archives the repository on Zenodo, versioned by the tag: .zenodo.json and CITATION.cff carry no version, since the packages have different ones. Then raise the lower bound downstream (canvodpy's filemap group) if the release needs it.

Then publish the package to PyPI by running publish_pypi.yml on the tag:

gh workflow run publish_pypi.yml --ref canvod-filemap-v0.2.0

It checks that the tag matches the package version, builds the package without the workspace's [tool.uv.sources], refuses a dependency on a URL (PyPI rejects those) and uploads with PyPI trusted publishing, so no token is stored anywhere. The upload waits for a maintainer's approval of the pypi environment. A package's dependencies must all be on PyPI first.

A new package under packages/ needs one step on PyPI before its first upload: add a pending trusted publisher for the package name (owner TUW-GEO, repository canvodpy-extensions, workflow publish_pypi.yml, environment pypi). The first upload creates the project and turns the pending publisher into a normal one. PyPI can refuse a second pending publisher while one is pending; then upload that package first. In the repository, the package's first just release starts its changelog and tags.
